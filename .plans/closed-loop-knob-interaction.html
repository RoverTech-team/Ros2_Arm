1. Objective

Rework the demo so the arm actually touches and actuates the panel's knobs in Gazebo with a closed feedback loop:

  • Every interaction is verified by physical state change of the knob (from /panel/joint_states), not by "the plan succeeded".
  • The arm's motion is verified (tracking check against the last commanded waypoint).
  • Contact is physically real: the j5 fingertip pushes levers over their detent, drags rotary knobs, presses fixed elements.
  • Scope: 17 elements — 12 knobs actuated (5 levers, 2 power, 5 rotary) + 5 fixed elements poked (electromagnet, 2 sockets, indicator, aruco tag).

4. Physics & geometry analysis (what actually works on a knob)

4.1 Frame mapping

panel_base fixed joint: (1.5, 0, 0) rpy (0,0,1.571)   →  world = (1.5 − panel_y, panel_x, panel_z)
panel spawns at z = 0.02 (launch)                      →  all element poses computed at runtime from TF
                                                          (panel_base_frame → world), never hardcoded.

4.2 Lever flip mechanics (5 levers: main_switch, lever_switch_1..4)

  • Joint: revolute about panel-x = world-Y (horizontal, along the face). Knob: box 0.008 × 0.035 × 0.006 protruding 35 mm from the face (panel +y → world −x). Tip world position: x ≈ 1.445, z = 0.240.
  • Torque about the pivot = F × 0.035 (knob arm). A side push (through the pivot axis) rotates nothing — only up/down pushes of the tip work.
  • Flip from θ=−1.57 (off) to +1.57 (on): the detent spring (now 0.4) opposes until the midpoint (max 0.63 N·m ≈ 18 N at the tip), then snaps the lever the rest of the way. The arm only needs to push the tip up ≈ 70 mm + margin ≈ 85 mm; the last ~50 mm of the push presses air (harmless).
  • Push contact: flat tip face under the knob tip (tool0 +z along world +z), or the j5 cylinder side-scoop (tool0 +z horizontal — much better for the 4-DOF arm). The IK probe (B1) picks per element.
  • Neighbor clearance: levers 57 mm apart; j5 fingertip Ø60 mm → ≤ 30 mm from center-line < 57 mm ✓ no neighbor contact.

4.3 Rotary / power knob spin (7 knobs: rotary_switch_1..5, power_switch_1..2)

  • Joint: continuous about panel-z = world-Z (vertical). Knob: cylinder r12 mm × 25 mm (rotary) / r16 × 30 mm (power), protruding from the face. Tip face at world x = 1.475 (rotary) / 1.470 (power).
  • Friction torque: 0.05 / 0.08 N·m. Radial presses rotate nothing (force through the axis) → press the side and drag tangentially; needed tangential force ≈ 0.08/0.012 ≈ 7 N; with a 15 N press and μ≈1.0, available ≈ 15 N ✓.
  • Drag: j5 side face tangent on the outer side of the row (j5 center 30 mm from the knob axis; neighbor knobs are 31 mm apart → nearest neighbor axis sits ≥ 61 mm from the j5 center → j5 surface never touches it ✓). Drag 60–80 mm along world-Y gives ≈ 3–4 rad ≫ 2 rad target.
  • Modes verified per element by the probe: side-press + drag along −Y or +Y; fallback: press the knob's end-face edge (offset contact) if the drag pose is unreachable.

4.4 Pokes (5 fixed elements)

Approach perpendicular to the face (tool0 +z along +X), stop 5 mm short, press 15 mm with the flat face. No panel-side verification (no sensor); success = execution + arm tracking. The foot (already merged) keeps the panel stable under all presses.

4.5 Tool0 rule

Every contact pose: tool0 is 40 mm BEYOND the physical tip along tool0 +z.
  tip_face_world = tool0_world + 0.04 · (tool0 z-axis)
All pre-contact and push-end poses below already apply this rule.

5. Proposed architecture

5.1 Per-element state machine

stateDiagram-v2
    [*] --> Approach: setPoseTarget(preContact) OMPL plan+execute
    Approach --> Push: hand-built 2-waypoint slow JTC goal (IK via setFromIK)
    Push --> Verify: settle 0.5 s, read /panel/joint_states
    Verify --> Retract: OK — OMPL back to clearance pose
    Verify --> RetryPush: FAIL (≤ 1 retry, +5 mm depth)
    RetryPush --> Verify
    Retract --> Next: arm-tracking check |q - q_last| < 0.05 rad
    Next --> [*]: success counted, dwell 500 ms

6. Blocker analysis

B1 — 4-DOF IK reachability of contact poses HIGH

What: The arm has only 4 DOF (j1 yaw, j2/j3 pitch, j5 roll, j4 fixed). The new approach phases need a defined tool0 orientation (push direction). At a given tool0 position, only a constrained set of orientations is reachable (tip direction set by j2+j3+fixed j4; roll by j1+j5). Poses like "tip pointing straight up at x≈1.4, z≈0.2" may be unreachable.

Impact: A planned push pose that fails IK would abort that element's interaction. Worst case: some knobs can't be pushed from the "nice" direction.

Verification experiment (E1 — IK probe, first implementation step): A throwaway node that, for each of the 17 elements × 2–3 orientation variants (flat-face lift, side-scoop, tip-down, drag ±Y), computes the pre-contact and push-end tool0 poses (40 mm rule applied), calls moveit::core::RobotState::setFromIK on the arm group, samples the joint-interpolated path and checks tool0 clearance vs the panel face (x=1.5 plane) and knob cylinders analytically. Output: per-element chosen push mode + waypoint joint table (yaml).

Mitigation: Each element has a fallback chain (lift↔scoop↔tip-down; drag −Y↔+Y; press edge). The probe hard-fails loudly on any element with zero feasible variants — at that point we redesign that element's push before writing demo code.

Residual risk: LOW (fallback chain is rich); only exotic cases (e.g., power_switch_2 behind the rotary row) could be marginal.

B2 — OMPL cannot plan into contact; the push segment is open-loop HIGH

What: The push-end pose is inside the knob — a collision-state goal. OMPL will refuse it (and the planning scene already contains the panel). The push must be a hand-built 2-waypoint JTC trajectory (IK at pre-contact → IK at push-end), executed open-loop like today's restamped trajectories.

Impact: No collision guarantees on the push segment; a bad interpolation could swing the tip into the panel face or a neighbor knob (rotary row: 31 mm spacing vs Ø60 mm fingertip — the chosen outer-side tangent geometry avoids this by construction, B-verified in E1).

Verification experiment: E1 samples the interpolated tool0 path for every push segment and asserts clearance (analytic check vs panel planes and knob cylinders, ≥ 5 mm). E2 (single-knob sim test) physically confirms one lever flip and one rotary drag with the panel upright.

Mitigation: Push segments are short (≤ 85 mm), collinear-ish, and executed at low velocity (≈ 20–40 mm/s). Push depth is capped; verify-then-retry adds +5 mm only on failure.

Residual risk: MEDIUM — the lever's mid-push spring snap can make the tip lose contact earlier than planned (harmless, see B3), and a slip during a rotary drag may need a 2nd pass (built-in retry).

B3 — Lever flip feasibility (force budget) MEDIUM — design decision applied

What: With detent_stiffness = 10, flipping requires 15.7 N·m at the pivot = ~450 N at the 35 mm tip — the arm cannot deliver that. With 0.4: max opposing torque 0.63 N·m ≈ 18 N at the tip; joint torques ≈ 18 N·m on j2/j3 (≈1 m arm) vs the 50 N·m limit ✓. URDF effort limit 5.0 N·m > 0.63 ✓ (spring never hits it).

Impact: Without the tuning, levers can only be "touched", never flipped. After tuning, the flip is physically achievable and the detent still latches the lever at ±1.57 (spring to nearest detent, 0 torque at the detent — holds position).

Verification experiment (E2): flip one lever manually in the demo world; confirm the lever snaps past the midpoint and rests at +1.57 while the panel stays put.

Residual risk: LOW. Minor: with a softer detent a lever could wobble from sim noise near the midpoint — irrelevant (threshold is 1.0 rad).

B4 — Rotary drag: friction, grip and neighbor clearance MEDIUM

What: Spinning a r12 mm knob by friction drag: needed tangential ≈ 7 N vs available ≈ 15 N (15 N press × μ≈1.0 default). Neighbor clearance requires the tangent on the outer side (j5 center ≥ 61 mm from any neighbor axis — verified analytically, §4.3).

Impact: If the tip slips (μ lower than expected, or press too light), the knob barely rotates and the verify (|Δθ| ≥ 2 rad) fails → retry; worst case repeated failures.

Verification experiment: E2 drags one rotary knob; measure Δθ and slip. If slip: (a) increase press depth (more normal force), (b) add surface friction <gazebo reference="rotary_switch_X_knob"><mu1>1.5</mu1><mu2>1.5</mu2></gazebo> in the xacro, (c) lengthen the drag.

Residual risk: MEDIUM until E2 passes; then LOW.

B5 — Verification reliability via /panel/joint_states MEDIUM

What: The panel JSB publishes knob positions (state interfaces only; the knob joints are driven by plugin SetForce + collisions — exactly what we need). Risks: (a) message rate/latency (settle 0.5 s before reading), (b) rotary joints are continuous → angle wrap (compare Δθ with wrap correction), (c) a lever that flips during the approach (arm grazes it) must be detected — snapshot before the push, not before the approach, and treat "already flipped correctly" as a pass.

Impact: False FAILs (retry churn) or false PASSes (if the snapshot is taken after contact).

Verification experiment: E3 full run — logged per-element before/after knob values must match the GUI-observed knob states.

Residual risk: LOW.

B6 — Mock-mode parity / feedback unavailability MEDIUM

What: In mock mode (use_gazebo:=false) there are no plugins and no physics — /panel/joint_states publishes static knob values. Knob verification would fail by design.

Impact: The mock demo (still part of the repo's regression suite) would go red.

Mitigation: The demo takes the interactivity from the same flag as the launch: interact := use_gazebo. In non-interactive mode, verification is skipped and success = execution + tracking (current semantics), keeping mock parity. Auto-fallback: if /panel/joint_states delivers no data within 10 s, degrade to the same mode with a warning.

Residual risk: LOW.

B7 — Panel stability under arm contact LOW — resolved by the foot

The invisible support foot (already merged, panel.urdf.xacro:46–53) extends the support polygon to x∈[1.40, 1.68] — the lumped COM (1.4986, 0.0166, 0.0189) projects 98 mm inside. All presses/drags of the new demo push the panel forward or sideways; the foot keeps it planted. Verification: E2/E3 assert the panel pose stays (0, 0, 0.005), zero rotation.

B8 — Execution time budget LOW

What: 17 elements × (approach ≈ 5–10 s + push ≈ 3–4 s + verify/settle ≈ 1 s + retract ≈ 5–8 s + dwell) ≈ 7–9 minutes vs ~2 min today.

Mitigation: Accept for v1 (it is a demonstration, not a benchmark); keep dwell at 500 ms; revisit only if a run exceeds 10 min. Optionally reduce approach velocity scaling to keep plans fast.

B9 — Trajectory timing vs controller velocity limits MEDIUM

What: The push goal is a 2-point trajectory. The JTC needs monotonic time_from_start and must respect the joint velocity limits (1.0 rad/s) while we want the push slow (~40 mm/s at the tip ≈ small joint rates ✓). The existing restamp trick (lines 205–213) already re-times flat plans — reuse it with a configurable push duration (3–4 s) and a first-waypoint check (must equal the live joint state, or the JTC rejects the goal).

Impact: Goal rejection / abrupt push if mistimed.

Verification experiment: E2/E3 log the JTC result code and arm tracking error during pushes.

  for (const auto & el : kElements) {
    double before = knobAngle(el);              // snapshot BEFORE approach (B5)
    bool ok = true;
    for (int attempt = 0; attempt <= 1 && ok; ++attempt) {
      // 1. APPROACH — OMPL, orientation-constrained pre-contact pose
      move_group.setPoseTarget(makeToolPose(el, pre_clearance, 0.0), "tool0");
      if (planAndExecute(move_group, action_client, executor) != OK) { ok = false; break; }
      // 2. PUSH — hand-built slow segment (IK via setFromIK), depth + attempt·5mm
      if (executePush(ikTwoWaypoint(el, attempt)) != OK) { ok = false; break; }
      // 3. VERIFY — settle 0.5 s, read /panel/joint_states
      ok = verify(el, before);                  // LEVER |θ|≥1.0 · ROTARY wrap-safe |Δθ|≥2.0
      if (!ok) RCLCPP_WARN(logger, "Knob '%s' did not verify (attempt %d), retrying deeper.",
                           el.name.c_str(), attempt);
    }
    // 4. RETRACT — OMPL back to clearance pose (+50 mm), execute
    planAndExecute(move_group, action_client, executor, retract_pose(el));
    // 5. ARM-SIDE CHECK — |current_joint − last_waypoint| < 0.05 rad (tracking feedback)
    ok &= armTracked();
    ok ? ++succeeded : ++failed;
    RCLCPP_INFO(logger, "%-18s %s (knob before=%.2f after=%.2f)",
                el.name.c_str(), ok ? "OK" : "FAIL", before, knobAngle(el));
  }
  RCLCPP_INFO(logger, "Demo complete: %d succeeded, %d failed.", succeeded, failed);
